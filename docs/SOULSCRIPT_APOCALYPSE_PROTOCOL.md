## V. THE RULE-BREAKER CHALLENGE: 12-POINT ATTACK MATRIX

To confirm that security boundaries hold under maximum hostile stress, the kernel substrate was subjected to twelve structural challenge vectors:

### 1. Challenge Architectural Assumptions
- **Hypothesis:** Kernel components assume in-memory state cannot be tampered with between verification and admission.
- **Threat Model:** Post-verification modification of hypothesis statements or observation IDs.
- **Verification:** `HostileHarnessTest.H-001` proves defensive cloning and digest binding reject any post-issuance modification with `ConstitutionalViolationException`.

### 2. Challenge Unnecessary Restrictions
- **Hypothesis:** Read-only queries or documentation items might be blocked unnecessarily by execution gates.
- **Threat Model:** Over-blocking harmless telemetry or L1 documentation.
- **Verification:** `PersistenceDisposition.HOLD_AS_L1` cleanly separates non-executable documentation from live L4+ execution paths without violating safety invariants.

### 3. Find Hidden Dependencies
- **Hypothesis:** `kernel-core` might have latent dependencies on host network libraries, system time, or UI runtimes.
- **Threat Model:** JDK HTTP server or socket leaks introducing host vulnerabilities into the pure kernel.
- **Verification:** Purified in GAP-06 by extracting all host HTTP servers into `desktop-bridge/` and replacing wall clocks with logical `KernelTimestamp(0L)`. `kernel-core` has zero external dependencies beyond `kotlinx.serialization`.

### 4. Find Authority Escalations
- **Hypothesis:** Calling `proposeSubstrateEvolution()` or high consensus among Pantheon catalysts can grant runtime execution rights.
- **Threat Model:** Persona consensus masquerading as execution authorization (`PERSONA ≠ AUTHORITY`).
- **Verification:** `HostileHarnessTest.H-008` & `H-010` prove that even 100% agreement among all 14 Catalysts produces only an un-admitted `TriggerProposal`. Execution requires an independent `AuthorizedActionToken`.

### 5. Counterexamples to Invariants
- **Hypothesis:** An observation without original raw text or source digest could be admitted if signed by an internal node.
- **Threat Model:** Sacred Provenance Law bypass (`Provenance Survives Transformation`).
- **Verification:** `HostileHarnessTest.H-006` proves that blank provenance fields trigger unconditional veto with `KernelRefusalReason.InsufficientProvenance`.

### 6. Falsify Verification Results
- **Hypothesis:** A hypothesis with an un-evaluated counter-evidence reference could sneak into `VERIFIED` status.
- **Threat Model:** Incomplete evidence graph resulting in false verification.
- **Verification:** `VerificationEngine` explicitly checks that missing counter-evidence or un-assessed counters force status to `UNRESOLVED`.

### 7. Hostile Inputs & Malformed State
- **Hypothesis:** Empty byte arrays, NaN or infinite thermal values could cause unhandled crashes or bypass guards.
- **Threat Model:** Denial of service via malformed floating point inputs.
- **Verification:** `RawVisualPayload.ingest(byteArrayOf())` throws `IllegalArgumentException`. Thermal temperatures `>= 42°C` or non-finite numbers immediately trigger `ThermalState.SOVEREIGN_STATE_FREEZE`.

### 8. Receipt Forgery Resistance
- **Hypothesis:** An external caller or rogue catalyst could construct an instance of `VerificationReceipt` directly.
- **Threat Model:** Forging a valid receipt with `vetoExecuted = false` to authorize malicious proposals.
- **Verification:** `VerificationReceipt` constructor is strictly `private`, and `VerificationReceipt.mint` requires an internal `VerificationReceiptToken` only mintable inside `VerificationEngine.verify()`.

### 9. Concurrency & Single-Use CAS Guarantees
- **Hypothesis:** Multiple concurrent worker threads could redeem the same `VerificationReceipt` simultaneously before state updates propagate.
- **Threat Model:** Double-spending / receipt replay race condition.
- **Verification:** `AtomicReceiptLedger` uses atomic compare-and-swap (`consumedReceiptIds`). `HostileHarnessTest.H-004` subjects the ledger to 16 concurrent threads making 64 simultaneous redemption attempts; exactly 1 attempt succeeds, and 63 are rejected.

### 10. Mistaking History for Current State
- **Hypothesis:** Stale receipts from a previous epoch or previous run could authorize actions in a new epoch.
- **Threat Model:** Replay attacks across system restarts or epoch transitions.
- **Verification:** `ExecutionAdmissionGate` validates `EpochNonce` and live snapshot state digests, rejecting stale epochs with `StaleEpochRefusal`.

### 11. Model Manufactured Certainty
- **Hypothesis:** High epistemic confidence or direct corroboration in `MetaInstructPolicyGate` could artificially increment verified insights.
- **Threat Model:** Self-referential score inflation.
- **Verification:** `CognitiveBrainTest.test_meta_instruct_cannot_create_verified_insight` confirms that `evaluateIngestionPipeline` cannot increment insight counts without an authoritative `VerificationReceipt`.

### 12. Proposal-to-Action Execution Leakage
- **Hypothesis:** A `TriggerProposal` object might be mutated or executed directly by the router without passing through the admission gate.
- **Threat Model:** `PROPOSED_ACTION = EXECUTED_ACTION` confusion.
- **Verification:** `TriggerProposal` is immutable. Admission produces an `AuthorizedActionToken` or `ExecutionReceipt`, leaving the original proposal untouched.
